# BK7258 T5-Board Audio DAC and fixed-32 kHz verification

Date: 2026-08-15

## Scope

Validate the first bounded T5-Board speaker-DAC contract through the public
NuttX audio ABI, including DMA/DAC/PA ownership, two complete open/close
sessions, Audio DVFS voting, fixed-32 kHz scheduler SysTick behavior and one
CP coordinated-standby restore.

The installed boot chain is preserved.  The download uses COM3 and writes only
the signed CP/AP primary application ranges after a non-halting public-trust
preflight.  COM4 is not opened.  The preflight reads only the installed
BL1/BL2 public-identity locations; BL1, BL2, manifests, slot B, LittleFS,
configuration, calibration, OTP/eFuse and lifecycle state are not written.

## Hardware and software contract

- T5-Board routes the SoC differential DAC to a CS8302M class-D amplifier.
  P28 is the active-high `SPK_CTL` input.  The amplified differential output
  terminates at connector P6; the board has no fitted loudspeaker.
- The selected board owns P28, active level and 10/30 ms PA delays.  The common
  AP lower half owns the DAC, repeat GDMA, two-frame DTCM ring, APB lifetime,
  refill worker and reverse teardown.
- `/dev/audio/pcm0p` intentionally publishes only mono PCM S16 at 16 kHz,
  using 320 samples/640 bytes per 20 ms DMA frame and eight explicit APBs.
- `RESERVE` acquires the board Audio client's 480 MHz SDK-tier vote.  A
  successful `RELEASE` occurs only after worker, APB, PA, DAC and DMA teardown,
  then drops that vote; the isolated validation aggregate returns to 120 MHz.
- The bounded scheduling order is producer 246 > Audio refill worker 245 >
  board-default RPTUN transport 225.  The worker refills the released DMA slot
  before publishing `DEQUEUE`; the newly ready feeder can then return one APB
  before another DMA completion forms a continuous worker chain.
- CP physical CPU0 and AP-primary physical CPU1 use external 32 kHz scheduler
  SysTick routes with reload 319 at 100 Hz.  For timer accounting, CPU DVFS
  refreshes their role-local DWT conversion, not the scheduler timer source.
- The dedicated CP validation profile is UART0/non-RTT and admits exactly one
  successful coordinated standby.  Its timer proxy freezes the pre-sleep
  phase, restores the immutable SDK leaf's timer changes and advances the
  NuttX arch-timer callback in a genuine SysTick exception.

## Causal correction history

The first complete lifecycle implementation returned every APB and released
all hardware, but a low-priority feeder was starved by the higher-priority
refill/callback worker.  The observed first underrun occurred after six
`DEQUEUE` messages had been published without one re-enqueue.  Using all eight
advertised APBs, holding the official Audio 480 MHz tier vote and ordering the
bounded feeder above the refill worker removed the underrun.  MCUboot
`18.6.72` then passed the Audio lifecycle, but its v4 diagnostic recorded 14
SysTick regressions while switching the core-clock-derived timer between
the AP-primary 120 and 480 MHz rates.

The scheduler timer was therefore moved to the official external 32 kHz
source.  The CP low-voltage leaf also changes SysTick reload and required an
arch-timer-aware sleep/restore proxy.  An initial `18.6.75` host artifact used
the shared RTT CP profile; its `up_idle` omitted `pm_idle` and the linker
discarded standby/prepare/restore, so it was rejected before download.  The
final pair uses a dedicated UART0/non-RTT one-shot CP profile and a build gate
that requires all four runtime symbols to be linked.

## Pre-flash and download evidence

The mandatory non-halting J-Link preflight read only the packaged BL1/BL2
public identity locations.  All three installed public fingerprints matched
the packaged trust contract before the loader was invoked.

The COM3 apps-only loader command contained exactly:

- CP `app_crc_flash.bin@0x11000-0x3f000`, writing
  `[0x011000, 0x050000)`;
- AP `app1_crc_flash.bin@0x165000-0x2a000`, writing
  `[0x165000, 0x18f000)`.

Both erase and write operations reported PASS and `Writing Flash OK`.  The
installed BL2 was intentionally preserved.  After reboot, the target was
observed at its preserved, public-identity-matched BL2 hold with
`VTOR=0x28020000`, release word zero and PC `0x280205a2`; the RAM-only `JLNK`
token then released the pair.
S1-1/S1-2 remained ON because this dedicated CP uses UART0 and Audio does not
claim P10/P11.

## Audio v5 hardware result

Two independent non-halting reads of `0x28054784` were byte-for-byte identical
for the complete 380-byte structure:

- magic/version/size `BDCV`/5/`0x17c`;
- terminal state `PASSED`, result 0, stage `DIAGNOSTIC`, cycles 2;
- 63 submitted APBs, 63 dequeues, two completes;
- one explicit `STOP` cycle and one natural `FINAL` drain cycle;
- 40,320 submitted bytes and 35,840 played bytes; the seven-frame difference
  is the bounded queue returned by the explicit-stop cycle;
- DMA alloc/start/stop/deinit/free, DAC start/stop and PA on/off all 2/2;
- 58 DMA frame completions and two final silent drain frames;
- underrun 0, first-underrun snapshot all zero;
- driver state `RESET`, first error 0, resources 0, PA final state OFF;
- producer priority 246, worker priority 245, both observed on AP CPU0;
- semaphore backlog maximum/events both zero;
- DMA interval minimum and maximum both `0x00927c00` DWT cycles, exactly
  20 ms at the active 480 MHz tier;
- worker-service maximum `0x003dc584` cycles, below one 20 ms frame;
- callback maximum `0x002fe158` cycles, also below one frame;
- validator tick regression, sampled `CLOCK_MONOTONIC` regression, sample
  errors and driver tick regression all zero;
- both sessions observed the AP-primary `120 -> 480 -> 120 MHz`; successful
  Audio vote and release counts were 2/2.

## CP one-shot PM and liveness result

Two complete non-halting reads of CP PM diagnostic `0x280127cc` were identical:

- magic/version/size `BMPD`/2/`0x40`;
- attempts 258, entered 1, aborted 257, wakeups 1;
- final reason 10 (`ENTERED`);
- sleep duration 14,406 us;
- compensated whole ticks 1;
- final AP sleep/clock votes and CP SDK awake masks all zero.

Before the first success, 257 entry attempts were aborted; the v2 diagnostic
does not retain the distribution of their reasons.  One-shot success freezes
the counters after the first real entry, so `aborted == attempts - 1` and the
stable second read establish the bounded contract.

Post-restore register and liveness evidence:

- `0x44010040 = 0x600807c8`, so CP bit 29 and AP-primary bit 30 are both set;
- CP SysTick CTRL low bits were 3, RVR was `0x13f`, and CVR changed from
  `0xb2` to `0x2d`, both values below 320;
- AP boot record was READY/error 0 and retained the 32 kHz CTRL/RVR snapshot;
- CPU2 record was SCHEDULER_ONLINE/error 0;
- RPTUN was CONNECTED/error 0 with flags `0x7f3f`;
- AP heartbeat advanced `0x11f -> 0x27e`;
- CPU2 heartbeat advanced `0x265 -> 0x523`;
- RPTUN CP/AP heartbeats advanced `0x7f/0x11f -> 0x110/0x27e`;
- the BL2 RAM release word returned to zero.

## Verification boundary

- This result proves the bounded NuttX audio/DMA/DAC/PA lifecycle and one CP
  standby restore.  It does not prove acoustic output because P6 has no fitted
  speaker.
- It covers only mono S16/16 kHz/320 samples/eight explicit APBs and an
  in-memory tone.  It does not cover shorter frames, other rates, compressed
  or file-backed producers, shared/mmap buffers, Wi-Fi/BT load, long soak or
  full duplex with the microphone.
- The zero regression counters cover the validator's Audio/DVFS transition
  observations plus the fixed-32 kHz register contract.  They are not a proof
  that every possible high-resolution read on every AP SMP core is globally
  monotonic.
- CP standby whole-tick compensation ran once.  AP coordinated standby still
  lacks AON elapsed-time compensation, so this record does not claim complete
  CP/AP standby time continuity.
- The installed BL1/BL2 public identities matched the packaged trust contract,
  and the boot chain was not replaced.  Development trust remains
  software-rooted; OTP/eFuse secure-boot enable and hardware rollback are
  outside this stage.
