# BK7258 T5-Board TF/SDIO host verification

Date: 2026-08-14

## Scope

Adapt the T5-Board V1.0.2 TF socket as two explicit hardware profiles:

- one-bit SDIO while retaining the CH342F UART0 download route;
- four-bit SDIO only after S1-1/S1-2 isolate that UART0 route.

This stage covers schematic/protocol review, board-owned lower-half changes,
profile preflight, and complete AP compile/link verification.  It does not
sign, package, download, reset the board, open COM4, or alter the installed
boot chain.

## Hardware contract

- TF CLK/CMD/D0/D1/D2/D3/CD are P2/P3/P4/P5/P10/P11/P6.
- P6 card detect is active low.  The socket circuit pulls CD high when no card
  is inserted.
- S1-1/S1-2 select the conflict on P10/P11 between TF D2/D3 and the CH342F
  UART0 download route.  They do not control the P0/P1 SWD/RTT route.
- Optional serial Flash U3 is marked NC.  If fitted, it shares the TF bus and
  the TF socket is not available to this profile.

The Beken SDK insertion helper enables an input pull-up and returns the raw
GPIO level; its caller treats a true/high result as no card.  The same SDK
documents that a card powers up in one-bit mode and sends ACMD6 before moving
to four-bit mode:

- `ap/middleware/driver/sd_card/sd_card_driver.c:112`
- `ap/middleware/driver/sd_card/sd_card_driver.c:462`

## NuttX protocol contract

The NuttX MMC/SD upper half sends ACMD6 only when
`SDIO_CAPS_1BIT_ONLY` is clear, then invokes `SDIO_WIDEBUS(..., true)`.
On media removal it unregisters the block device and restores one-bit mode:

- `nuttx/include/nuttx/sdio.h:478`
- `nuttx/drivers/mmcsd/mmcsd_sdio.c:2732`
- `nuttx/drivers/mmcsd/mmcsd_sdio.c:2781`
- `nuttx/drivers/mmcsd/mmcsd_sdio.c:4389`

Therefore a one-bit lower half must return `SDIO_CAPS_1BIT_ONLY`; returning
zero would incorrectly allow the upper half to command the card into four-bit
mode while the controller remained one-bit.

## Implementation

- The shared lower half reports `SDIO_CAPS_1BIT_ONLY` or `SDIO_CAPS_4BIT`
  according to the selected profile.
- Both profiles initialize the host in one-bit mode.  Four-bit transition is
  owned by the standard NuttX ACMD6 plus `widebus` sequence.
- T5-Board owns the pin mux and active-low P6 card-detect interpretation.
- HPWORK polls card detect every 100 ms and reports insertion/ejection through
  the standard NuttX media callback outside interrupt context.
- The bounded validator mounts `/dev/mmcsd0` as FAT, creates one unique 4096
  byte file, calls `fsync`, closes and reopens it, verifies the pattern, removes
  only that file, unmounts, then repeats after one eject/reinsert cycle.  It
  never formats the card.
- Four-bit selection requires
  `CONFIG_BK7258_T5_BOARD_SDIO_D2_D3_ISOLATED=y`; paired-profile preflight also
  rejects an active CP/BL1 UART0 conflict.

## One-bit real-board download and first boot

The existing download entry ran the merged non-halting J-Link trust preflight
before `bk_loader`; all three installed BL1/BL2 public fingerprints matched.
The apps-only write set contained exactly:

- CP `app_crc_flash.bin@0x11000-0x3d000`
- AP `app1_crc_flash.bin@0x165000-0x28000`

Both erase/write operations passed.  BL1, BL2, manifests, secondary slot,
LittleFS and other data regions were not included in the loader arguments.
COM3 was used for download and COM4 was not opened.

After reboot the selected MCUboot pair reached the intentional BL2 SWD hold at
PC `0x280205a2`.  Writing the existing SRAM release token allowed CP/AP to
start; CP RTT channel 0 produced an NSH prompt and the AP validation diagnostic
became valid with bus width one.

The card was physically inserted throughout this boot, but P6 read high and
the diagnostic ended as state `FAILED`, stage `WAIT_INITIAL`, result
`-ETIMEDOUT`, cycles/bytes zero.  Board initialization completed and the SDIO
controller was active, so this exposes an unresolved mismatch between the
assumed active-low card-detect contract and the actual T5-Board CD path.  The
worker never reached mount or media I/O; this run establishes correct
download/boot/worker startup but neither passes nor fails SDIO/FAT operation.
A card-removed P6 sample is required to distinguish reversed polarity from an
unusable card-detect contact.

## Remaining real-board validation

The original temporary working filenames disappeared, but the keys had been
created by the earlier project workflow rather than supplied by an external
owner store.  Existing current-domain alias copies were checked against the
three recorded public fingerprints and matched exactly:

- BL2 MCUboot SPKI SHA-256:
  `df8b7893df6afea30da3b212f26f42646404e5e7d9feae0ec2615d0c90cea26e`
- BL1 SEC1 SHA-256:
  `6d17866e4d3572eff3a9b9fc1c8d33b9a1add71a13784b2feff385c38883106c`
- BL1 X||Y SHA-256:
  `e82597007f132d2415c64ea88f0dc75bce67e574d6e9943931a0b97a849fcc02`

The working filenames were restored from those same-key copies.  No new key,
unrelated trust domain or root rotation was used.  The root cause was keeping
agent-generated development keys under temporary names and then treating one
missing name as proof that the identity was gone.  The merged public-contract
and non-halting J-Link preflight, not a filename, remain authoritative.

The remaining sequence is:

1. Compare P6 with the card removed, correct the board card-detect policy, then
   reset/release and validate one-bit with S1-1/S1-2 ON.
2. Power/reset after changing both switches OFF, then validate four-bit.
3. Record mount, write/read verification, unmount, eject, reinsert, and repeat
   results through RTT/J-Link while keeping P0/P1 SWD/RTT and COM3 available.
