# BK7258 T5-Board TF/SDIO host verification

Date: 2026-08-14 to 2026-08-15

## Scope

Adapt the T5-Board V1.0.2 TF socket as two explicit hardware profiles:

- one-bit SDIO while retaining the CH342F UART0 download route;
- four-bit SDIO only after S1-1/S1-2 isolate that UART0 route.

This record covers schematic/protocol review, board/chip separation, profile
preflight, signed builds, non-halting level sampling and apps-only hardware
validation.  COM4 is not opened and the installed boot chain is not written.

## Hardware contract

- TF CLK/CMD/D0/D1/D2/D3 are P2/P3/P4/P5/P10/P11.
- The schematic labels P6 as active-low card detect, but the physical board
  reads P6 high both with media inserted and removed.  P6 therefore remains
  schematic metadata and is not used as a presence source.
- S1-1/S1-2 select the conflict on P10/P11 between TF D2/D3 and the CH342F
  UART0 download route.  They do not control the P0/P1 SWD/RTT route.
- Optional serial Flash U3 is marked NC.  If fitted, it shares the TF bus and
  the TF socket is not available to this profile.

The optional Beken SDK insertion helper enables an input pull-up and returns
the raw GPIO level; its caller treats high as no card.  SDK builds without
`CONFIG_SDCARD_CHECK_INSERTION_EN` probe without this check.  The same SDK
documents that a card powers up in one-bit mode and sends ACMD6 before moving
to four-bit mode:

- `ap/middleware/driver/sd_card/sd_card_driver.c:112`
- `ap/middleware/driver/sd_card/sd_card_driver.c:462`

## NuttX protocol contract

The NuttX MMC/SD upper half sends ACMD6 only when
`SDIO_CAPS_1BIT_ONLY` is clear, then invokes `SDIO_WIDEBUS(..., true)`.
On media removal it unregisters the block device and restores one-bit mode:

- `nuttx/include/nuttx/sdio.h:478`
- `nuttx/drivers/mmcsd/mmcsd_sdio.c:2732`
- `nuttx/drivers/mmcsd/mmcsd_sdio.c:2781`
- `nuttx/drivers/mmcsd/mmcsd_sdio.c:4389`

Therefore a one-bit lower half must return `SDIO_CAPS_1BIT_ONLY`; returning
zero would incorrectly allow the upper half to command the card into four-bit
mode while the controller remained one-bit.

For a slot without insertion information, NuttX requires `SDIO_PRESENT()` to
remain true and probes once during slot initialization.  Consequently the
T5-Board profile disables `MMCSD_HAVE_CARDDETECT`, does not claim hotplug and
requires the card to be inserted before reset.

## Implementation

- The validated lower half reports `SDIO_CAPS_1BIT_ONLY`.  The reserved
  four-bit path would report `SDIO_CAPS_4BIT`, initialize in one-bit mode and
  leave ACMD6 plus `widebus` to NuttX, but it is rejected with the current SDK
  bundle as described below.
- The hidden chip host owns only the controller protocol.  T5-Board owns the
  slot binding, pin mux, fixed-media policy and S1 route assertions.
- T5-Board status is always present after board initialization.  The callback
  ABI remains implemented, but no P6 poll worker is compiled or queued.
- The bounded validator first mounts `/dev/mmcsd0` as FAT.  If the medium has a
  GPT protective MBR, it registers up to 32 partitions and tries them from
  largest to smallest until the FAT driver accepts one.  It then creates one
  unique 4096-byte file, calls `fsync`, closes and reopens it, verifies the
  pattern, removes only that file, unmounts, and repeats once on the same fixed
  media.  It never formats the card.
- The controller retains continuous card clocking across CMD7 and the normal
  transfer-clock switch, matching official v3.1.1.9 and Tuya behavior.  CMD12
  alone retains the SDK's reset/gate/reset sequence.  Command polling clears
  only command W1C status and preserves a coalesced data IRQ.
- T5 TF profiles use `MMCSD_MULTIBLOCK_LIMIT=1`.  NuttX therefore issues
  CMD17/CMD24 for media I/O and does not expose the immutable CPU-FIFO SDK's
  observed second-block pre-read overflow to the filesystem.
- Four-bit selection requires
  `CONFIG_BK7258_T5_BOARD_SDIO_D2_D3_ISOLATED=y`; paired-profile preflight also
  rejects an active CP/BL1 UART0 conflict.

## Removed-card level and fixed-media correction

With the card removed, four consecutive non-halting J-Link reads of the AON
GPIO6 register at `0x44000418` returned `0x00010009`; input bit 0 remained high.
To eliminate firmware pin-configuration differences, the register was
temporarily set to the SDK-equivalent input plus pull-up state.  Four reads then
returned `0x0015003d`, again with input bit 0 high, after which the original
`0x00010009` value was restored.  No flash region was written.

Combined with the earlier inserted-card high level, this proves that P6 has no
usable insertion transition on the tested T5-Board.  Reversing active-low to
active-high would incorrectly report both physical states as present and was
therefore rejected.

The correction separates the layers as follows:

- hidden `BK7258_SDIO` remains the chip host/controller capability;
- `BK7258_T5_BOARD_TF_SLOT` owns the physical slot and selects the host;
- board config declares card detect unavailable and leaves P6 untouched;
- T5-Board profiles explicitly set `MMCSD_HAVE_CARDDETECT=n`;
- the validator runs two same-card FAT cycles without claiming hotplug;
- profile preflight rejects a T5-Board TF profile that omits the fixed-media
  upper-half policy.

The corrected one-bit CP/AP pair then completed a full signed MCUboot build
with version `18.6.49` and security counter `102`.  SDK checksum, partition,
Factory and RPTUN layout gates passed.  The public trust-contract SHA-256
remained `b2a8e35256b97a0dd4fef6da253225d770001f4f20743d44bf8e9cc5f3b97c7e`.
The resolved AP configuration contains the board TF slot, SDIO, HPWORK and FAT,
but explicitly omits `MMCSD_HAVE_CARDDETECT`; the final ELF retains the fixed
card-present hook and validator diagnostic while omitting the media-poll worker.

## SDIO failure localization and correction

The first fixed-media boots reached `/dev/mmcsd0` but timed out before a FAT
read.  Non-halting register snapshots and command-specific error logs separated
three independent issues:

1. The wrapper had started clearing `clk_gate_on` when switching from ID to
   transfer clock.  The last completed response remained CMD7 and register
   `0x458d0044` confirmed automatic clock gating.  Official v3.1.1.9, Tuya and
   the historical wrapper all keep continuous clocking through CMD16 and SCR.
   Removing the ordinary transfer-clock gate change allowed enumeration and
   sector reads to proceed.
2. Multi-block CMD18 then overflowed while the immutable SDK's CPU-FIFO path
   pre-read the second block.  Waiting before draining and reducing the clock
   to 13 MHz did not close the block-boundary race.  The final profiles use the
   standard NuttX `MMCSD_MULTIBLOCK_LIMIT=1` policy at the board/profile layer,
   retain 20 MHz, and use single-block CMD17/CMD24 transfers.
3. The test card is a Home Assistant OS GPT medium.  The first GPT fallback
   incorrectly assumed its largest partition was FAT and received `-EINVAL`.
   The validator now tries parsed partitions until the FAT driver accepts one;
   it selected `/dev/mmcsd0p1`, named `hassos-boot`.

`/dev/mmcsd0` existing by itself was not treated as proof of completed SD
initialization: the NuttX probe can register the block driver after CSD parsing
even when a later SCR/transfer step fails.

## Historical four-bit boundary (superseded)

At this checkpoint four-bit was not yet claimed as validated.  The original
AP `libdriver.a` bundle
defines SDIO V2 but not `CONFIG_SDCARD_BUSWIDTH_4LINE`; its private data-setup
helpers overwrite the runtime width from that compile-time macro and therefore
force one-bit operation.  A genuine four-bit stage needs a separately identified
four-bit-capable SDK bundle or an SDK-side ABI correction, followed by S1-1/S1-2
UART0 isolation and a fresh signed build plus real-board validation.  Merely
selecting the NuttX four-bit profile is insufficient.  Both the build preflight
and the wrapper now fail this combination closed rather than generating a
misleading four-bit image.

transfer, and exports a read-only runtime-width diagnostic.

The first four-bit boot proved one successful controller-width transition but
failed GPT/FAT recognition.  Non-halting register reads separated the causes:

- `0x440100c0 = 0x66111122`: P2/P3/P4/P5 were SDIO mode 1;
- `0x440100c4 = 0x44000000`: P10/P11 remained UART0 mode 0;
- P10 was `0x00150378` and P11 was `0x00000378`; their low `0x378`
  pull/drive/function fields matched, but the full registers were not
  identical;

- S1-1/S1-2 had also remained ON during that first run, so the CH342F route was
  still physically connected to D2/D3.

The board wrapper now follows the official SDK and Tuya ownership sequence:
it explicitly releases the default-mapped profile pins before selecting SDIO
group 0.  P5 is not in the pinned default table and already starts unmapped.
One-bit profiles do not release P10/P11 and therefore retain their UART0 route.

## Post-hardware release hardening

No runtime source changed after the genuine four-bit PASS.  Host-side release
handling was tightened before publication:

- SDK setup now rejects missing, duplicated or mismatched provenance and binds
  it to the selected version/role, manifest, final `libdriver.a` and, for the
  four-bit AP variant, the exact ordered overlay pair;
- SDK import holds the shared dual-build lock, supports the normal fresh-clone
  state with tracked metadata but ignored binaries, and rolls the bundle,
  manifest and provenance back together on command failure or a catchable
  signal;
- dual-image cleanup now recognizes an interrupted AP four-bit configuration
  before changing profiles, while the broken-`Make.defs` recovery path still
  performs a configured distclean.

The three supported current bundle/role checks passed.  An isolated temporary
tree exercised 12 provenance negative cases (missing file/field, duplicate or
wrong identity, wrong manifest/archive binding, and wrong four-bit overlay
binding); all 12 failed closed and the repository hashes were unchanged.  A
complete signed `18.6.63` / security-counter `117` four-bit dual-image rebuild,
Factory/RPTUN verification, role-specific link-map checks, shell syntax and
`git diff --check` passed.  This post-pass build was not downloaded.  The
one-bit image retains its earlier real-board FAT baseline and the changed
shared path has compile/profile review, but a second one-bit board run after
the P2/P3/P4 ownership remap was not performed in this stage.
