# 一、概述

<span class="reference">openvela</span> 的**视频编解码**框架借鉴了 Linux 内核的 **Video for Linux 2 (V4L2)** 框架，并重点实现了其 **Memory-to-Memory (M2M)** 模型。在 Linux 中，<span class="reference">v4l2m2m</span> 是一个标准模块，专用于处理需要内存作为输入和输出的硬件，如视频编解码器（Codec）。

通过在 <span class="reference">openvela</span> 中引入 <span class="reference">v4l2m2m</span> 接口，我们成功统一了**视频编解码驱动框架**，为**南向芯片厂商**提供了标准的编解码驱动接入层。这使得第三方硬件可以便捷地集成到 <span class="reference">openvela</span> 生态中，显著降低了开发和适配成本。

V4L2 M2M 整个框架的核心点在于复用 V4L2 框架的 <span class="reference">frame buffer</span> 管理模块，增加一路 <span class="reference">output queue</span>，用于接收编解码器输入数据，原始 <span class="reference">capture queue</span> 用于存放编解码器的输出数据。下图以视频解码为例，展示使用M2M框架的处理流程。

![img](https://vela-open-doc.cnbj1.mi-fds.com/vela-open-doc/1781005755294_001.png)

> **说明**：在V4L2 M2M框架中，<span class="reference">output queue</span> 为数据的**输入端**。<span class="reference">capture queue</span> 始终作为**输出端**，主要是为保持与 V4L2 Camera 框架的队列使用习惯一致。

# 二、框架总览

<span class="reference">openvela</span> V4L2 M2M框架采用经典的**分层**设计，将通用逻辑与设备特定实现解耦。这种模式类似于 <span class="reference">openvela</span> 音频驱动中的**上层 (Upper-Half)** 和**下层 (Lower-Half)** 模型。

对上层应用来说，<span class="reference">openvela</span> V4L2 M2M框架提供了兼容 Linux 标准的接口给应用使用；对底层的驱动开发者来说，<span class="reference">openvela</span> V4L2 M2M 框架简化了适配接口，可快速完成驱动开发。

![img](https://vela-open-doc.cnbj1.mi-fds.com/vela-open-doc/1781005755399_002.png)

  - **V4L2 通用层 (Upper-Half):**
    
      - 由 <span class="reference">v4l2\_core</span>、<span class="reference">v4l2\_cap</span> (用于摄像头等捕捉设备) 和 <span class="reference">v4l2\_m2m</span> (用于编解码设备) 模块构成，有对应的 <span class="reference">capture ops</span> 和 <span class="reference">codec ops</span>。
      - 该层负责响应来自应用程序的 <span class="reference">ioctl</span> 系统调用，处理 V4L2 的核心逻辑、缓冲区管理和事件机制。它为下层驱动定义了一套标准的操作函数集（ops）。

  - **设备驱动层 (Lower-Half):**
    
      - 由具体的硬件驱动程序构成，例如文档中用作示例的 <span class="reference">sim\_camera</span> 和 <span class="reference">sim\_decoder</span>。
      - **驱动开发者的核心工作**就是实现这一层。通过填充并注册特定的 <span class="reference">ops</span> 结构体，驱动即可与通用层无缝对接。

当系统启动后，下层驱动（如 <span class="reference">sim\_decoder</span>）会**注册相应的设备节点（如 <span class="reference">/dev/video1</span>）**。应用程序通过标准**文件接口访问这些节点**，请求经由 V4L2 通用层，最终分派到对应的**下层驱动进行处理**。

# 三、框架详解

本章将深入剖析 <span class="reference">openvela</span> V4L2 M2M Codec 驱动的内部机制，涵盖其核心组件、接口定义、数据交互模型及关键开发实践。

## 1、核心组件

<span class="reference">openvela</span> 的 <span class="reference">v4l2m2m</span> 实现借鉴了 Linux 的成熟设计，其架构围绕以下四个核心组件构建：

  - **<span class="reference">codec\_ops\_s</span>**: **下层驱动的核心实现**。它定义了一套操作回调函数，功能对标 Linux 的 **<span class="reference">v4l2\_ioctl\_ops</span>**。驱动开发者的主要工作就是实现此接口。
  - **<span class="reference">v4l2\_ops\_s</span>**: **V4L2 通用 <span class="reference">ioctl</span> 接口**。这是一个框架层（Upper-Half）的接口，M2M 通用层会提供一个该接口的实例 (<span class="reference">g\_codec\_vops</span>)，它负责接收上层请求并调用到下层驱动的具体实现 (<span class="reference">codec\_ops\_s</span>)。
  - **<span class="reference">codec\_file\_s</span>**: **设备实例管理器**。每当应用程序 <span class="reference">open</span> 设备节点时，框架会创建一个 <span class="reference">codec\_file\_s</span> 实例来管理该会话的上下文，包括独立的缓冲区队列，从而实现多实例支持。并且 m2m 中对 <span class="reference">buffer</span> 的分配管理也是通过<span class="reference">codec\_file\_s</span>来完成。
  - **<span class="reference">codec\_mng\_s</span>**: **设备顶层管理器**。在驱动注册设备节点（如 <span class="reference">/dev/video1</span>）时，框架会创建一个 <span class="reference">codec\_mng\_s</span> 实例，作为该设备在内核中的全局句柄。

![img](https://vela-open-doc.cnbj1.mi-fds.com/vela-open-doc/1781005755500_003.png)

> **图注:** 此图清晰展示了 <span class="reference">v4l2\_ops\_s</span> 作为通用入口，如何通过 <span class="reference">codec\_mng\_s</span> 和 <span class="reference">codec\_file\_s</span> 最终调用到驱动开发者实现的 <span class="reference">codec\_ops\_s</span>。

## 2、关键代码

V4L2 M2M 框架的逻辑主要分布在以下几个文件中：

  - <span class="reference">nuttx/drivers/video/v4l2\_core.c</span>: V4L2 框架的总入口，定义了顶层文件操作 **<span class="reference">g\_v4l2\_fops</span>**，并将请求分发至 Camera 或 M2M 的实现。

  - <span class="reference">nuttx/drivers/video/v4l2\_m2m.c</span>: **M2M 通用层 (Upper-Half)**。实现了 M2M 设备的通用逻辑，定义了 <span class="reference">g\_codec\_fops</span> 和 <span class="reference">g\_codec\_vops</span>，对应<span class="reference">file\_operations</span>和<span class="reference">v4l2\_ops\_s</span>。**这是下层驱动主要交互的模块**。参考 <span class="reference">sim\_decoder</span>，<span class="reference">codec</span> 的开发主要是 <span class="reference">codec\_ops\_s</span>的实现，以及完成输入输出 <span class="reference">buffer</span> 的对接。

  - <span class="reference">nuttx/drivers/video/video\_framebuff.c</span>: V4L2 通用的缓冲区管理模块，为上层提供统一的缓冲区申请、排队和生命周期管理能力。

  - <span class="reference">nuttx/drivers/video/v4l2\_cap.c</span>: Camera 设备的通用实现，Codec 开发一般不直接涉及。包括 <span class="reference">image capture</span> 和 <span class="reference">video capture</span> ，定义了 Camera 的<span class="reference">g\_capture\_fops</span>和<span class="reference">g\_capture\_vops</span>，对应<span class="reference">file\_operations</span>和<span class="reference">v4l2\_ops\_s</span>。

## 3、接口与数据结构

本节详细介绍 M2M 驱动开发中涉及的关键数据结构和操作集。从顶层到底层顺序进行讲解。

### <span class="reference">codec\_mng\_t</span>

<span class="reference">codec\_mng\_t</span>是设备总管理结构体，在调用<span class="reference">codec\_register</span>驱动注册接口的时候，动态分配，并与<span class="reference">driver</span>实现接口进行绑定，以此实现将上层应用的请求转换到<span class="reference">driver</span>请求中。  

    struct codec_mng_s
    {
      struct v4l2_s v4l2;        // v4l2 框架通用结构体，框架实现
      FAR struct codec_s *codec; // v4l2 driver实现接口，Vendor实现
    };

### <span class="reference">v4l2\_s</span>

在<span class="reference">openvela</span>V4L2框架中，一个V4L2设备对应的一个<span class="reference">v4l2\_s</span>结构体，封装了指向设备具体操作的两个核心函数指针表：<span class="reference">vops</span> 和 <span class="reference">fops</span>。

  - <span class="reference">vops</span>: 指向 <span class="reference">v4l2\_ops\_s</span> 结构体，定义了所有 V4L2 相关的 <span class="reference">ioctl</span> 操作。
  - <span class="reference">fops</span>: 指向 <span class="reference">file\_operations</span> 结构体，定义了标准的 VFS 文件操作（如 <span class="reference">open</span>, <span class="reference">close</span>, <span class="reference">poll</span> 等）。

根据设备类型，<span class="reference">v4l2\_s</span> 会被实例化并指向不同的实现，例如 Camera 设备对应 <span class="reference">g\_capture\_vops</span> 和 <span class="reference">g\_capture\_fops</span>，而 M2M Codec 设备则对应 <span class="reference">g\_codec\_vops</span> 和 <span class="reference">g\_codec\_fops</span>。  

    struct v4l2_s
    {
      FAR const struct v4l2_ops_s      *vops;
      FAR const struct file_operations *fops;
    };

### <span class="reference">v4l2\_ops\_s</span>

<span class="reference">v4l2\_ops\_s</span> 是 V4L2 框架中**通用**的 <span class="reference">ioctl</span> 操作函数集。它定义了所有 V4L2 设备（包括 Camera 和 M2M Codec）可能支持的操作的原型。当一个 <span class="reference">ioctl</span> 请求通过 VFS 传递到 V4L2 核心层后，最终会通过该结构体中的函数指针分发到具体设备类型的通用层（如 <span class="reference">v4l2\_m2m.c</span>）进行处理。  

    struct v4l2_ops_s
    {
      CODE int (*querycap)(FAR struct file *filep,
                           FAR struct v4l2_capability *cap);
      CODE int (*g_input)(FAR int *num);
      CODE int (*enum_input)(FAR struct file *filep,
                             FAR struct v4l2_input *input);
      CODE int (*reqbufs)(FAR struct file *filep,
                          FAR struct v4l2_requestbuffers *reqbufs);
      CODE int (*querybuf)(FAR struct file *filep,
                           FAR struct v4l2_buffer *buf);
    // ... 其他标准V4L2操作 ...

### <span class="reference">codec\_s</span>

<span class="reference">codec\_s</span>结构体中目前只包含<span class="reference">codec\_ops\_s</span>结构体，即只需要<span class="reference">driver</span>适配<span class="reference">codec\_ops\_s</span>接口即可。后续会更新实际需求，对<span class="reference">codec\_s</span>结构体进行扩展。  

    struct codec_s
    {
      FAR const struct codec_ops_s *ops;
    };

<span class="reference">codec\_ops\_s</span> 是下层驱动（Lower-Half）必须实现的操作回调函数集合。驱动开发者需要根据硬件能力，实例化一个 <span class="reference">codec\_ops\_s</span> 结构体并填充其函数指针。<span class="reference">codec\_s</span> 结构体则将该操作集与驱动的私有数据绑定起来。  

    /* 下层驱动需要实现的操作回调函数集合 */
    struct codec_ops_s
    {
      /* 设备生命周期管理 */
      CODE int (*open)(FAR struct codec_s *codec, void *arg);
      CODE int (*close)(FAR struct codec_s *codec);
    
      /* 流控制 */
      CODE int (*capture_streamon)(FAR struct codec_s *codec);
      CODE int (*output_streamon)(FAR struct codec_s *codec);
      // ... 其他 streamon/streamoff 及 available 回调 ...
    
      /* 标准 V4L2 IOCTLs 的具体实现 */
      CODE int (*querycap)(FAR struct codec_s *codec, FAR struct v4l2_capability *cap);
      CODE int (*capture_enum_fmt)(FAR struct codec_s *codec, FAR struct v4l2_fmtdesc *f);
      // ... 其他 ops，如 g_fmt, s_fmt, g_parm, s_parm, events, cmds 等 ...
    };
    
    /* 将 ops 与驱动私有数据绑定 */
    struct codec_s
    {
      FAR const struct codec_ops_s *ops;
      FAR void                     *priv;
    };

> **说明:** <span class="reference">codec\_ops\_s</span> 中的许多操作是**可选**的，驱动可以根据硬件支持的功能选择性地实现。

### <span class="reference">codec\_file\_t</span>

<span class="reference">codec\_file\_t</span> **(**<span class="reference">struct</span>**<span class="reference"></span>**<span class="reference">codec\_file\_s</span>**)**: **设备文件实例**，在 <span class="reference">open</span> 时创建，其 <span class="reference">priv</span> 指针用于关联下层驱动的私有数据。它是实现多实例支持的关键，每个设备节点 <span class="reference">open</span> 一次，就会创建一个新的<span class="reference">codec\_file\_t</span>，对应不同的 <span class="reference">codec context</span>，实现了多实例的需求。  

    struct codec_file_s
    {
      codec_type_inf_t  capture_inf; // capture queue buffer info
      codec_type_inf_t  output_inf;  // output  queue buffer info
      sq_queue_t        event_avail; // 存放可用事件单项链表
      sq_queue_t        event_free;  // 存放空闲事件单项链表
      codec_event_t     event_pool[CODEC_EVENT_COUNT]; // 事件队列
      FAR struct pollfd *fds;
      FAR void          *priv; // 存放driver的私有数据，在调用open接口时，driver可以将私有结构体指针存放在priv中，方便下次框架调用接口的时候使用
    };

  - **<span class="reference">codec\_type\_inf\_t</span>(<span class="reference">struct codec\_type\_inf\_s</span>)**: 用于管理单一类型（Capture 或 Output）的缓冲区信息。  
    
        struct codec_type_inf_s
        {
          video_framebuff_t bufinf;     /* video framebuff 队列 */
          FAR uint8_t       *bufheap;   /* for V4L2_MEMORY_MMAP buffers */
          bool              buflast;
        };

  - **<span class="reference">codec\_event\_t</span>(<span class="reference">struct codec\_event\_s</span>)**: 用于订阅 <span class="reference">event</span> 和管理 V4L2 事件的内部结构。  
    
        struct codec_event_s
        {
          sq_entry_t        entry;
          struct v4l2_event event;
        };

### <span class="reference">g\_codec\_fops</span>

<span class="reference">g\_codec\_fops</span> (<span class="reference">struct file\_operations</span>)为 M2M 框架提供的通用全局文件操作实例接口，是一个全局静态变量。驱动注册后，<span class="reference">v4l2\_core</span> 中的 <span class="reference">fops</span> 会直接调用 <span class="reference">codec</span> 的 <span class="reference">fops</span>，完成 <span class="reference">codec</span> 的 <span class="reference">open</span>/<span class="reference">close</span>/<span class="reference">mmap</span>/<span class="reference">poll</span>操作。  

    static const struct file_operations g_codec_fops =
    {
      codec_open,            /* open */
      codec_close,           /* close */
      NULL,                  /* read */
      NULL,                  /* write */
      NULL,                  /* seek */
      NULL,                  /* ioctl */
      codec_mmap,            /* mmap */
      NULL,                  /* truncate */
      codec_poll,            /* poll */
    };

### <span class="reference">g\_codec\_vops</span>

<span class="reference">g\_codec\_vops</span> (<span class="reference">struct v4l2\_ops\_s</span>)为M2M框架提供的通用全局操作实例接口，是一个全局静态变量。 实现了 V4L2 的通用 <span class="reference">ioctl</span> 命令接口。这些函数作为**适配层**，其内部会调用下层驱动在 <span class="reference">codec\_ops\_s</span> 中注册的对应回调函数。例如，<span class="reference">codec\_querycap</span> 函数最终会调用 <span class="reference">(codec-\>ops-\>querycap)(...)</span>。  

    /* M2M 通用层提供的 v4l2_ops_s 实现 */
    static const struct v4l2_ops_s g_codec_vops =
    {
      codec_querycap,                   /* querycap */
      NULL,                             /* g_input */
      NULL,                             /* enum_input */
      codec_reqbufs,                    /* reqbufs */
      codec_querybuf,                   /* querybuf */
      codec_qbuf,                       /* qbuf */
      codec_dqbuf,                      /* dqbuf */
      // ... 其他20余个已实现的接口 ...
      codec_decoder_cmd,                /* decoder_cmd */
      codec_encoder_cmd                 /* encoder_cmd */
    };

## 4、缓冲区交互模型

V4L2 M2M 框架的核心是其双队列缓冲区模型。内存由 M2M 通用层根据用户空间的 <span class="reference">VIDIOC\_REQBUFS</span> 请求进行分配和管理。下层驱动通过以下 API 与通用层进行缓冲区数据交换：

  - **获取缓冲区**:
    
      - <span class="reference">codec\_output\_get\_buf()</span>: 获取一个包含待处理数据（如 H.264 码流）的输入缓冲区。
      - <span class="reference">codec\_capture\_get\_buf()</span>: 获取一个空闲的、用于存放处理结果（如 YUV 数据）的输出缓冲区。

  - **归还缓冲区**:
    
      - <span class="reference">codec\_output\_put\_buf()</span>: 将已处理完毕的输入缓冲区归还给 M2M 通用层。
    
      - <span class="reference">codec\_capture\_put\_buf()</span>: 将已填充数据的输出缓冲区归还给 M2M 通用层，使其可被应用层读取。  
        
            FAR struct v4l2_buffer *codec_output_get_buf(FAR void *cookie);
            FAR struct v4l2_buffer *codec_capture_get_buf(FAR void *cookie);
            
            int codec_output_put_buf(FAR void *cookie, FAR struct v4l2_buffer *buf);
            int codec_capture_put_buf(FAR void *cookie, FAR struct v4l2_buffer *buf);

## 5、开发注意事项

  - **缓冲区申请:** 输入 (<span class="reference">output</span>) 和输出 (<span class="reference">capture</span>) 缓冲区均由用户空间通过 <span class="reference">ioctl</span> 的 <span class="reference">VIDIOC\_REQBUFS</span> 命令触发申请，内存由 M2M 通用层统一分配和管理。
  - **队列操作:** 受限于 <span class="reference">video\_framebuff</span> 的当前实现，不建议一次性将所有请求的 <span class="reference">output</span> 缓冲区都入队到 M2M。推荐的模式是：在入队一个新的 <span class="reference">output</span> 缓冲区之前，先尝试出队所有已处理完的缓冲区。
  - **延迟初始化:** <span class="reference">sim\_decoder</span> 示例将 <span class="reference">sim\_openh264dec</span> 的初始化推迟到 <span class="reference">output\_streamon</span> 回调中执行。这种做法避免了在驱动探测（probe）阶段进行不必要的硬件初始化和关闭，是一种推荐的优化实践。
  - **Flush 操作:** 在调用 <span class="reference">output\_streamoff</span> 时，驱动应确保硬件中缓存的所有帧都被完全处理并输出。<span class="reference">sim\_decoder</span> 通过设置 flush 标志并调度工作队列来清空解码器内部的剩余数据。
