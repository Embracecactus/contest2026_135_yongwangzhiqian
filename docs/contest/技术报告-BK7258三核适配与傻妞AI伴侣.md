## 三、正文

### 3.1 绪论

#### 3.1.1 项目背景与问题定义

**应用场景.** 大模型让"AI 伴侣"类硬件成为消费电子热点：用户希望拥有一台可独立对话、有形象表达、可随身携带的智能终端。但此类产品的典型形态（Wi-Fi 联网音箱、带屏故事机）存在三个具体痛点：

1. **唤醒与隐私矛盾**：云端语音识别要求音频持续上传，家庭/随身场景隐私敏感；而端侧资源又不足以承担本产品选定的云端大模型；需要把常态监听与按次联网分开。
2. **形象表达单薄**：多数产品是"会说话的盒子"，缺少低成本、高辨识度的拟人化表达通道；单屏方案要么被文字界面占据，要么成本失控。
3. **平台门槛过高**：主流 AI 玩具方案依赖手机 SoC 或 Linux 应用处理器（成本、功耗、启动时间均劣），而 RTOS 级 MCU 方案通常绑定厂商闭源 SDK，应用生态割裂，无法复用通用 AI 框架。

**行业与平台痛点.** 本作品同时瞄准 openvela 生态的一个真实空白：openvela 官方适配主要覆盖若干既有芯片平台，而 Beken BK7258 这颗在网络摄像头、AI 玩具品类大量出货的 Wi-Fi 6 三核芯片需要本项目新增 openvela 支持——SDK 中含厂商专用启动、无线与多核机制，本项目需要将这些能力适配到 openvela，而不是把原 SDK 应用直接改名。选择该芯片意味着：既要做产品，又必须先造平台。

**目标定义.** 交付一台可独立运行、可审计、可复现的 AI 伴侣原型：
- 本地唤醒 + 云端大模型对话（小米 MiMo），一次唤醒可连续追问，无语音自动退出；
- 可拍照并由多模态大模型回答"看到了什么"；
- 双 160×160 屏以眼睛动画表达情绪与状态，支持表情资源在线安装；
- 手机 App 完成开箱配网/认领/控制/固件 OTA；
- 全链路安全：签名启动、加密记忆、受保护传输、设备所有权认证。

#### 3.1.2 技术难点

| # | 难点 | 具体挑战 |
|---|---|---|
| 1 | **三核非对称启动** | BK7258 为 CPU0 先启、CPU1/CPU2 由应用层唤醒的三核架构，BootROM 协议、Flash 透明 CRC 格式、启动核身份、多核释放时机均需从闭源二进制与 SDK 交叉逆向确认；openvela 官方模板假设单镜像单核 |
| 2 | **CP/AP 双镜像协同** | CP（CPU0）与 AP（CPU1+CPU2 SMP）是两个独立 NuttX 镜像，必须设计核间总线（RPTUN/RPMsg/RPMsgFS）、syslog 汇聚、健康监督与故障恢复；两个镜像共享 Flash/PSRAM/中断控制器，所有权必须严格划分 |
| 3 | **端侧唤醒在 MCU 上落地** | 无 NPU、无 DSP，仅 640 KB SRAM + 8 MiB PSRAM；目标词为中英文混合的“你好，openvela”，需在 MCU 上完成前端特征（KWS 专用 microfrontend）与全 INT8 卷积推理，且满足实时性与误报率约束 |
| 4 | **资源受限下的多模态链路** | 音频采集/播放、摄像头 JPEG、双屏刷图、网络 TLS 全部在 640 KB 级内部 SRAM 上共存；长连接 TLS 握手、Base64 编码、图片上传都存在内存峰值风险 |
| 5 | **可审计的安全启动与 OTA** | 厂商预编译 bootloader 不可审计且绑定私有 OTA 引擎；需要自研可复现的 BL1、接入开源 MCUboot BL2，并实现“同槽签名 CP/AP 成对升级 + A/B + trial 确认 + 回滚计数” |
| 6 | **端侧缺口的算法数据** | 唤醒词为自定短语，无公开数据集；中文合成语音与真实录音分布差异大；需要自建数据/训练/量化/评测工具链并给出可复现报告 |

#### 3.1.3 创新点

1. **平台层——BK7258 三核 openvela 适配**：以"CP/AP 配对系统"替代官方模板的单镜像假设，自研 BL1（源码 bootloader）+ NuttX MCUboot BL2 + 同槽签名/回滚 OTA 链，并把芯片层与板级层彻底分离，同一套 SoC 实现复用于 T5AI-Core、T5-Board、AIDK AI Toy 三块物理板。
2. **端云融合的语音架构**：端侧 47 KB 全 INT8 DS-CNN 做唤醒（隐私友好、断网可用），云端 MiMo 完成 ASR/对话/TTS；一次唤醒进入连续会话（不把每句播放结束当作退出），联网失败时报告错误，本地显示/唤醒不依赖云推理；请求中断恢复验收仍有限，会话上下文由官方 Agent 框架管理。
3. **"眼睛即界面"的交互差异化**：双 160×160 圆屏不做文字界面，只做拟人化眼睛动画（16 组表情 + 离线兜底表情，支持眨眼与左右顾），表情资源包支持 Wi-Fi 安全安装与热更新，以低成本获得高辨识度的人格表达。
4. **可审计的安全与隐私设计**：签名启动链、设备认领（possession proof + 证书 pin）、AES-256-GCM 加密记忆快照（与设备身份绑定、可远程删除）、受保护 TLS（证书/主机名/有效期持续校验）——安全设计进入产品主路径而非事后补丁。
5. **AI-Native 工程方法**：开发过程广泛使用 AI；当前导出日志样本含 162 个会话、4.09 亿 token、3,439 次编辑工具事件，沉淀"AI 结论视为待验证假设、一切结论以可复现命令与原始证据确认"的工程方法，并把 8 个自研操作技能（Skill）随仓库交付，覆盖唤醒词训练、Android/语音实机联调、发布验证与 PR 流程。

### 3.2 系统方案设计

#### 3.2.1 系统总体架构

设备有 **两个 openvela/NuttX 实例**：CP 单核运行于 CPU0，AP SMP 运行于 CPU1/CPU2；CPU2 不是第三个独立系统。设备外另有 Android 控制 App 和所选云服务，Bootloader 属于启动阶段而不是常驻应用节点。整体架构如下：

                 │  ASR mimo-v2.5-asr  |  LLM mimo-v2.5(-pro)     │

                 └───────────────────────▲────────────────────────┘

**各节点角色与运行的系统：**

| 节点 | 运行系统 | 角色 |
|---|---|---|
| CP（CPU0） | openvela/NuttX（UP，单核） | 启动 owner；Flash/文件系统、Wi-Fi/BT 控制器、OTA 引擎、健康监督、syslog 汇聚、按键入口 |
| AP（CPU1+CPU2） | openvela/NuttX（SMP，双核） | 应用 owner；官方 Agent 框架与会话、语音全链路、双屏显示服务、摄像头、加速度计、加密记忆（NFC 驱动已适配，未接入产品交互） |
| BL1 + BL2 | 裸机 + NuttX MCUboot | 安全启动：BL1（自研）→ MCUboot BL2 → 校验并启动同槽签名 CP/AP |
| Android App | Android 10+（minSdk 29） | 可选控制台：认领/配网/控制/OTA 供包/眼睛资源/Token Plan 配置；不中转对话音频 |
| 云端 MiMo | 云服务 | ASR / 多模态对话 / 流式 TTS |

**三条主要数据流：**

1. **语音流（核心链路）**：MIC1 采集 → AP 端 KWS 前端（TFLM microfrontend）持续推理 → 命中唤醒词 → 播本地提示音并进入会话 → 录音（16 kHz/mono/PCM16）→ 云端 ASR → Agent 会话（含工具调用）→ 云端 LLM → 流式 TTS（SSE）→ 播放；播放结束继续收音，无语音则退出回待机。
2. **视觉流**：Agent 工具 `camera_capture` → 唯一摄像头 owner（V4L2/GC2145）抓 640×480 JPEG → base64 data-URI → 同一 LLM 多模态问答 → TTS 播报。
3. **配置与升级流**：App BLE GATT 认领（possession proof）→ 配置 Wi-Fi/云凭据并持久化 → 固件 OTA 时 App 起本地 HTTPS 供包、设备经签名包校验后写非活动槽 → trial 确认或回滚；眼睛资源包走同一供包与安装事务。

#### 3.2.2 方案论证与选型

**（1）开发板选型理由**

| 候选板 | 硬件特点 | 结论 |
|---|---|---|
| **AIDK AI Toy（选定，产品板）** | BK7258 三核；双 GC9D01 160×160 LCD；GC2145 DVP 摄像头；MFRC522 NFC；SC7A20H 加速度计；MIC1 + MIC2（AEC 参考）；焊接式 SD NAND；CN10 马达接口 | 本项目三板中最贴近双眼 AI 伴侣形态；当前产品实测以此板为准，NFC 未接入产品流程 |
| T5AI-Core V1.0.1 | 最小系统板，无屏无摄像头 | 作为首块 bring-up 取证板与最小回归基线（启动链、NSH、PSRAM、驱动验证） |
| T5-Board V1.0.2 | RGB LCD、TF 卡、CH342F 双 UART、拨码开关 | 运行小海豚 Dolphin 工具应用，同时验证芯片/板级分层复用；不把傻妞全功能结论推广到该板 |

选择标准是"芯片能力全覆盖 + 产品形态倒推"：先在三块板共用的芯片层打透，再用产品板做垂直闭环，避免把某块板的电气事实写成芯片属性。

**（2）与备选方案的对比**

| 维度 | 备选方案 A：Beken ARMINO SDK 直接开发 | 备选方案 B：单镜像单核运行 | **本方案：CP/AP 配对 + openvela** |
|---|---|---|---|
| 系统基础 | FreeRTOS 私有框架 | openvela 单镜像 | openvela 双镜像（CP UP + AP SMP） |
| 生态复用 | 以厂商中间件为主 | 需重新划分控制器与应用资源 | 官方 Agent 框架、TFLM、media、VFS、RPMsg 全复用 |
| 可审计性 | bootloader/SDK 闭源部件不可审计 | 依赖厂商启动链 | 自研 BL1 源码化 + MCUboot 开源 BL2 |
| 并发能力 | 沿用 SDK 的多核模型 | 本项目未做同负载单核对照测试 | 三核分工，AP 双核 SMP 承载应用 |
| 结论 | ✗ 放弃（违背平台适配初衷，且不可审计） | ✗ 放弃（架构与芯片设计不匹配） | ✓ 采用 |

**（3）端 / 云职责划分与降级策略**

划分原则：**隐私敏感与实时性敏感的处理放端侧，语义智能放云侧。**

| 能力 | 端侧（设备） | 云侧（MiMo） |
|---|---|---|
| 唤醒检测 | DS-CNN INT8 本地推理（离线可用） | — |
| 语音识别 | 采集/编码/上传 | ASR（整段 16 kHz WAV） |
| 对话与工具调用 | Agent 会话/上下文/工具执行 | LLM 推理（可切换 pro/快速模式） |
| 语音合成 | 流式解码与播放；唤醒应答音本地内置 | TTS（SSE 流式 PCM） |
| 视觉 | 单帧抓拍与 JPEG 编码 | 多模态理解（同 LLM） |
| 记忆 | 设备本地加密快照（3 轮上限） | 上下文窗口由会话管理 |

**断网 / 弱网降级策略（实测口径）：**
- **唤醒与提示**：唤醒检测、启动提示音、眼睛动画全部本地，断网仍可唤醒与表达状态；
- **对话**：ASR 传输失败返回明确错误码并回到待机，不伪造回答；网络恢复后下一轮自动可用（热点断开后自动重连/DHCP 恢复已实测；"请求中途断网恢复"未取得正式唤醒样本，不作为已通过项）；
- **连接成本**：同一受保护配置内共享 TLS 恢复会话（减少重复握手），更换配置不复用旧缓存，证书/主机名/有效期校验始终开启；
- **App 侧**：明确显示离线/失败状态（Listening/Thinking/Speaking/Offline 状态机），不显示伪造的在线成功。

#### 3.2.3 关键模块设计

**（1）CP/AP 核间通信（RPTUN / RPMsg / RPMsgFS）**

- 物理层：MBOX0 FIFO 硬件 mailbox（`tdata/tid/sid/fifo_*` 寄存器组）作为 doorbell + 共享内存传输消息体；
- 协议层：NuttX 官方 RPTUN/OpenAMP/RPMsg，CP 与 AP 各跑一个 rpmsg 端点；服务发现用 Name Service；
- 文件通道：AP 经 RPMsgFS 访问 CP 的 LittleFS（用于 CP 侧持久数据读取）；
- 日志通道：AP 无 console（维护配置关闭 `CONFIG_DEV_CONSOLE`），syslog 经 RPMsg 汇聚到 CP 的 UART0 输出，前后缀区分 `cp`/`ap` 与 SMP CPU 号；
- 关键设计：RPMsg 队列长度、缓冲与重连路径都做过 stress（5,000 条 MBOX0 消息、六场景各 100 次）；单核 mailbox 深度为 1，靠 worker 轮询（1 ms）驱动。

**（2）CP 对 AP 的健康监督与故障恢复**

- 三路健康信号（心跳/状态/错误计数）+ 故障注入测试闭环；
- 异常时 CP 侧 fail-closed：AP 未就绪则产品功能不注册，避免半可用状态静默运行；
- 实测各版本启动窗口 supervisor `faults=0 / recoveries=0`（见 3.5）。

**（3）语音全链路的"单 owner"协同**

- 音频采集与播放共用唯一 media owner（官方 media recorder/player），半双工仲裁避免播放时采集造成回声；
- 唤醒（KWS）与 ASR 采集互斥：唤醒后先播本地应答并排空、再开采集；无语音端点超时退出；
- TTS 流式 PCM 经官方 voice channel 播出，播放结束继续收音（连续会话），由会话状态机统一调度。

**（4）显示协同（双屏眼睛）**

- 显示服务运行在 AP，独占 QSPI0/QSPI1 两路 GC9D01；
- 表情资源为离线图集（17 个表情档，含 offline 兜底），渲染时做帧缓存与动画调度（眨眼、左右顾），动画由 worker 缓存 5 帧（约 256,000 B）；
- Agent 可通过工具 `device_control(eyes=...)` 触发表情，与系统状态（listening/offline）叠加优先级：系统状态 > 情绪表达；
- 资源包支持 App Wi-Fi HTTPS 安装（`SHNEYE1` 格式校验 + CRC32），安装后热更新并持久化。

**（5）交互模块**

- **按键与 App 控制（两类交互入口）**：物理按键在 CP 侧 `/dev/buttons` 采样，经 RPMsg 上报 AP（序列号/租约/时钟回退防误拼长按）；K1/K3 音量步进 ±15、K2 3 秒长按关机；按键不直接调用媒体，仅产生语义事件。App 经 BLE GATT（TLS 1.2 上的 `provision-v1`/控制协议）承载音量、人物风格、隐私记忆开关、唤醒灵敏度、回答模式、云模型 ID 等设置，全部保存并回读确认；
- **相机交互**：语音触发（"这是什么"）即调用 `camera_capture`，不回传原图到手机、不落盘。

### 3.3 核心算法与技术原理

#### 3.3.1 端侧 AI：全 INT8 DS-CNN 唤醒词模型

**（1）模型结构与量化**

唤醒词为大赛统一词"你好，openvela"；App 可导入并切换用户自定义模型，但当前分类器是 silence / unknown / 单个目标词三分类，不是三个唤醒词同时识别。下面说明 64 通道实验候选；公开固件内置的 32 通道模型另行区分。端侧模型为**深度可分离卷积网络（DS-CNN）**，全 INT8 量化：

| 项目 | 参数 |
|---|---|
| 网络 | `ds-cnn-conv64-10x4-s2xf4`：基础卷积 10×4（64 通道）→ 4 组深度可分离卷积（DW3×3-S2 → DW3×3-S2 → DW9×3 → DW9×3）→ PW64 → BN/ReLU → 全局池化 19×10 → Dense3；导出算子 6 种（CONV_2D/DEPTHWISE_CONV_2D/AVERAGE_POOL_2D/FULLY_CONNECTED/RESHAPE/SOFTMAX） |
| 输入 | `[1, 149, 40, 1]`：约 3 s 音频、40 维特征、20 ms 帧跳 |
| 输出 | `[1, 3]`：silence / unknown / 唤醒词 三分类 |
| 模型体积 | **47,672 B**（SHA256 `536ebba8…b83c`） |
| 量化 | 全 INT8（权重与激活），输入量化参数 3.5725 / 零点 −128 |
| 特征前端 | TFLM `microfrontend`（KISS FFT → filterbank → PCAN → log），41 项前处理源码哈希随模型元数据冻结 |
| 算力占用 | 约 **6.80 M MAC/次**推理（32 通道基线为 2.43 M）；32 通道模型板端 arena 已用 **40,692 B**；64 通道模型主机评估 arena 80,320 B（板端未测，不作冒充） |
| 感受野 | 150 帧 = 3,000 ms |

**（2）训练数据与配方（工具可复用，私人语料不公开）**

| 数据 | 规模 | 来源与许可 |
|---|---|---|
| 正例（唤醒词合成） | 234 条 | Kokoro v1.1-zh 58 个训练音色合成（Apache-2.0，15 个音色留出做泛化） |
| 负例（unknown） | 798 条 | FLEURS `cmn_hans_cn` dev 359 条录音扩展（CC-BY-4.0） |
| 静音/噪声 | 88 条 | MS-SNSD；保留原署名及混合许可边界，不能统一宣称 CC0 |
| 真实人声 | 38 片段（131.968 s，1 位说话人，仅入训练） | 用户授权录音，自动标注候选 |
| 合计 | 1,120 条（验证 69 / 测试 113） | 脚本化切分与血缘记录（`source_id`） |

数据增强：增益 1.0/0.25/0.1 三档、模拟房间 3 次反射（18–180 ms）、噪声标准差 3–15、负例 400 ms 随机位移、来源加权。训练环境：TensorFlow 2.15.1 + Keras，Adam，24 轮上限，batch 32，最终选定第 22 轮（验证损失 0.1215）。

> 资产边界：训练语料（含 1 位说话人的授权录音）与候选权重按记录的授权范围（本地训练/评估）**不随仓库分发**；上表构成、许可来源、配方与全部评测口径已在本报告完整披露，评审可核对方法而不依赖原始音频。

**（3）端侧部署与触发策略**

- 推理框架：openvela 官方 **TFLite Micro**（`apps/mlearning/tflite-micro`），产品构建以 `-Os` 优化压缩体积；
- 推理节拍：**300 ms/次**（`BKVOICE_KWS_INFER_HOPS=15`）；
- 判定策略（决策算法）：连续 **2 次**超阈值才触发、得分释放阈 0.20、触发后 **1,000 ms** 冷却，显著抑制瞬时误报；
- 阈值演进：模型打包元数据记录的冻结策略阈值为 0.85；产品源码默认下调至 0.60（App 可配 50–90% 并持久化回读），实板 631 档位为 0.65——三处口径分开陈述，不用源码值冒充实板生效值；
- 位宽容错：模型与前端的量化误差经"host TFLM vs 桌面 TFLite 最大分差 1/256"校验，只证明这批输入的算子/量化一致性，不替代板端性能或声学效果验收。

**（4）评测口径（严格区分合成与真人）**

- 独立测试集（41 条合成会话、369 秒）：正例分类命中 20/20、严格连续流命中 20/20，负例误识别 1/87；正例来自 15 个与训练隔离的合成音色，但不是 20 位独立真人；
- 已见用户 38 片段（录音已入训，非独立泛化）：片段分类命中 38/38、达固定阈值 38/38（旧模型 37/38、33/38）；**原始连续录音的严格区间命中仅 3/38（旧模型 7/38，退步）**，词尾后 1,000 ms 内关联 29/38、合计 32/38；严格命中退步不作为通过项；
- 一个"放宽正例词尾窗口"的对照训练（合成验证 18/18 触发）使同一批真人片段的连续流触发从 38 次降为 28 次，依据**训练前冻结的否决条件**被否决，未打包上线；
- 主机算子兼容：69 条验证 + 113 条测试 + 38 条已见片段（220 份相同 C 前端特征）上，主机 TFLM 与桌面 TFLite 最大分数差 1/256、类别与阈值决策差异为 0（主机证据，非板端结果）；
- 结论：该 64 通道候选在模型元数据中状态为 `candidate`、`accepted=false`（原因：真实语料与流式证据未达标）；它已通过 App 模型导入通道在实板激活并完成 SHA 回读确认，但板端推理耗时未测、真人泛化未通过，因此**未升级为固件内置默认模型**（内置模型仍为 32 通道、23,640 B）；合成验证不能替代真人泛化，连续录音的严格时间窗命中是当前主攻方向（见 3.7）。

#### 3.3.3 关键机制设计

**（1）唤醒—会话状态机（决策）**

一次唤醒进入连续会话：唤醒 → 播本地应答（IndexTTS-2.5 离线生成、0.975 s / 31,208 B 内置 PCM）→ 自动收音 → ASR/LLM/TTS → 播放结束继续收音；无有效语音端点超时后回待机（Trigger 重新武装）。会话内追问不重复唤醒、不重复提示音；上下文由官方 Agent Session 管理。该机制解决"每句播放结束=退出会话"的体验断点。

**（2）Agent 工具调用与安全护栏（融合决策）**

- 设备能力以**工具 provider** 注册进官方 Agent 工具注册表，LLM 只能生成受限语义请求，物理执行受产品状态机约束：
  - `device_status`（音量/心情/电池电压，未标定项返回未知而不猜测）；
  - `device_motion`（加速度，声明为加速度计而非陀螺仪）；
  - `device_control`（音量 0–100、心情 5 档、振动 1–100 ms、表情）；
  - `camera_capture`（唯一摄像头 owner 抓拍并交 LLM 多模态）；
- 所有工具经 `tool_guard` 检查后才允许执行；工具能力与请求校验经内部评审批次加固；
- 永不暴露：任意 GPIO/寄存器、Shell、裸 Flash 写入、密钥读取——设备侧不做"大模型裸手脚"。

**（3）单资源 owner 与仲裁（调度）**

音频（采集/播放）、摄像头、显示、存储各自唯一 owner，跨所有者请求通过消息与状态机串行化：TTS 播放期间麦克风采集静音保护（此时振动请求返回 `-EBUSY` 而不强行执行）；摄像头抓拍复用唯一 V4L2 owner，不创建第二采集任务；显示动画 worker 不覆盖已确认的资源就绪状态。

**（4）加密持久记忆（数据融合）**

- 存储位置：CP 侧 LittleFS（`/cpdata/shaniu/`），AP 通过受控接口访问；
- 格式：SMH1 会话快照（最多最近 3 轮、每段上限 4,096 字），AEAD 封装（**AES-256-GCM**、96-bit 随机 nonce、52 B 开销，头部/长度/密钥代参与认证）；
- 密钥绑定：策略记录（SMP1，72 B）以 SHA256(设备控制身份) 绑定，只有已认领设备可解密；删除动作为换数据密钥并写空快照；
- 与官方框架的关系：**投影**而非并行运行时——启动时把快照恢复到官方 Session，回答提交后写回快照；旧格式加密数据只读兼容，不删除、不迁移旧文件。

**（5）OTA 决策机制（安全更新）**

BL1（自研、源码可审计）→ MCUboot BL2（NuttX 官方）→ 同槽签名 CP/AP 成对启动；升级写非活动槽（A/B），采用 **trial 确认制**：新固件启动后需通过健康确认（generation/映射/supervisor 健康/计数连续/时间单调同时满足，5,000 ms 窗口、250 ms 轮询）才落盘 confirmed，否则回滚旧槽；回滚计数与来源版本绑定在发布清单中。整机有线恢复与 apps-only OTA 是两条独立路径，OTA 不可替代整机恢复（密钥轮换与信任根差异在文档中显式区分）。

**（4）适配难点与解决方案（真实缺陷案例）**

| 难点 | 根因 | 解决方案 |
|---|---|---|
| 启动核身份（CPU0 vs CPU1） | 厂商 SDK 目录命名含糊，运行时 core-id 字为软件约定不可靠 | 三条独立证据链（分区表/启动源码/多核唤醒位置）+ 板上裸探针坐实 **CPU0 = boot master** |
| Flash 透明 CRC 格式 | 每 32 B 数据后硬件追加 2 B CRC16，地址需物理↔逻辑换算，闭源打包器 | 从 BootROM 协议逆向出格式，自研开源 packer 与闭源工具**逐字节等价**（测试向量 + 真实 bin 验证） |
| UART RX 输入不通 | 4 个叠加缺陷：取位偏移、`rx_enable` 未开、三道中断门未开、FIFO 阈值=0 导致 ISR storm | 逐层定位并修复（chip 层 serial 驱动），NSH 交互式 console 打通 |
| 多核释放 | 两家 bootloader 都不释放 CPU1/CPU2，且需 cache/MPU/WDT handoff 确定化 | BL1 补齐 reset/cache/MPU/core-power normalization；应用层按 SDK 语义唤醒 CPU1/CPU2 并跑通 SMP |
| SDK 命令响应非幂等 | 厂商 `wait_cmd_response` 为队列消费式，重复调用会吞下一条响应 | 读 SDK 实现确认语义，只在发送端消费一次，接收端只读缓存 |
| 驱动并发缺陷 | worker 线程生命周期、ISR 与任务 TOCTOU、ISR re-arm 竞态等 6 类真实缺陷 | 双轮代码审查 + 修复模式沉淀（STOP-join、取消集合、ISR 快照、running 门闩、幂等核实、配置断言） |
| 三核内存/存储所有权 | 双镜像共享 Flash/PSRAM，容易互相踩踏 | 芯片层统一 stage table + 板级分区 CSV；CP 建堆后释放 AP，AP 只建私有堆 |

**（5）三块物理板复用验证**

同一套芯片层实现复用于三块板：T5AI-Core（16 MiB PSRAM 全容量测试、驱动基线）、T5-Board（TF 卡固定介质语义、双 UART 拨码冲突管理）、AIDK AI Toy（产品全功能）。新板只需增加板级目录（引脚/总线/分区）与配置选择，不改芯片层——这验证了分层边界的可复用性。

**（2）运行时 Skill（/data/agent/skills/）的定义与触发场景**

设备端 Agent 采用 openvela 官方运行时技能机制，**技能即文件**：

- **目录与格式**：`/data/agent/skills/<name>.md`（扁平结构，产品启动时预置该目录）；首行为 `# 标题`，其后为简短描述段落（摘要用）与技能步骤正文；
- **加载**：每次构建模型上下文时枚举技能目录，把"标题 + 描述"摘要注入系统提示词（`skill_loader_build_summary`），模型据此知道有哪些技能可读；
- **热更新**：对目录列表/文件大小/时间做哈希，检测到变化即刷新摘要（`skill_loader_check_changed`/`skill_loader_refresh`），无需重启；
- **触发场景**：① 关键词触发——用户说"技能列表/有什么技能"即返回已装技能清单；② 指令触发——`/skill` 装载技能清单；③ 任务匹配触发——模型依据摘要判断请求命中某技能后，用 `read_file` 读取技能正文，按其中步骤调用既有工具执行（读取技能文件后的回答会强制走模型生成，不会短路成工具回显）；
- **产品集成现状（已内置 + 可扩展）**：固件**内置一个设备助手技能**——`device-assistant.md` 随启动写入 `/data/agent/skills/`（`/data` 为 tmpfs，故每次开机重装；内容只描述本产品真实注册的工具，不含凭据与用户数据，构建产物中可验证该文本）；同时把官方 `read_file` 工具接入产品工具 provider，供模型读取技能正文；设备核心能力（设备状态/运动/控制/拍照）以原生工具 provider 注册并受 `tool_guard` 校验，与技能机制并存。该目录可装载额外技能，但它是 tmpfs：手工写入不保证重启保持；技能步骤只能调用当前已注册且获准的工具，不自动获得定时器或新硬件能力。**实板验证（2026-09-20，`18.6.399+635`）**：串口确认 `bk7258: runtime skill installed: /data/agent/skills/device-assistant.md`、工具提供者注册（`bk7258-device`/`bk7258-camera`）与工具表构建（2,012 B，含 `read_file`），语音链路就绪（`wake ready=1`）并由用户完成语音验证。

**补充：AI 工具对开发效率的提升**

- **根因分析提速**：UART RX 四个叠加缺陷、RPMsg `ENOMEM`（CPU1 线程栈未回收）等疑难问题，通过"AI 读源码 + 提出假设 + 主机/实板双向验证"的方式定位；双轮代码审查（59 Pattern + 深层安全）在 11 个驱动中一次性发现 6 类真实并发/生命周期缺陷；
- **交叉核对**：闭源 bootloader 逆向结论、SDK 语义（如命令响应非幂等）、分区/符号/ABI 契约，由 AI 在 SDK 源码、二进制反汇编、数据手册之间交叉验证，人工只审核关键结论；
- **工程规模化**：140 份日期化验证文档、Master Plan（3,800+ 行）与 60+ 候选迭代的身份/哈希/证据链均由 AI 维护，人工专注实板操作与决策。

**问题与解决方式**

1. **AI 结论可能错误**（最早期的典型：把启动核误判为 CPU1）：确立"**AI 结论视为待验证假设**"原则——源码所有权、分区、符号、构建产物、硬件结果必须由可重复命令或原始证据确认，并由板端探针/串口日志裁决；
2. **上下文漂移与陈旧结论**：以仓库内主文档（Master Plan + 事实所有权表）为唯一事实源，旧状态显式标注"历史边界"，不把历史路线图当现行路线；
3. **越权风险**：构建/烧录/推送/密钥操作全部设授权门禁，AI 不擅自执行破坏性动作，交付物不含私钥与私有数据；
4. **日志与隐私**：AI Coding 日志按大赛格式导出（`logs/lijian/`），但硬件原始证据与 AI 日志分目录管理，技能文档不打包会话、凭据与私有设备数据。

### 3.7 总结与展望

#### 3.7.1 成果总结

本作品在一条完整的产品链上交付了两层成果：

1. **平台层**：为 Beken BK7258（三核 Cortex-M33）建立可复用的 openvela/NuttX 适配——CP/AP 配对镜像、RPTUN/RPMsg 核间总线、BL1+MCUboot 安全启动、A/B trial OTA、11 类外设驱动；三块物理板复用同一芯片层；此前平台成果在官方比赛仓基线中；281/281 是历史主机回归记录，不是本次 635 全套重跑。
2. **产品层**：交付可独立运行的 AI 伴侣"傻妞"——本地唤醒（47,672 B INT8 模型）、MiMo 云端连续对话（端到端 4.5–8.6 s）、拍照识物、双屏眼睛表情、加密记忆、物理按键、Android 控制台与签名 OTA 全链路；实板完成多次唤醒闭环、真实 App OTA（`18.6.398+634`）；635 完成 Skill/语音/显示验证。历史 14 分钟观察不冒充当前长期稳定性验收。

**关键量化指标**：离线合成负例误触发 1/87；对应启动观察窗口 supervisor faults/recoveries=0；AP 固件 ~1.6 MB、链接余量 ~455 KB；签名 OTA 包 3.42 MB。**明确边界**：已入训用户录音的离线严格时间窗命中 3/38（未达标，不是本次实板成功率）、性能数据为单样本、功耗未实测——这些均已如实标注，不因相邻功能通过而升级。

**目标受众**：18–35 岁、对情感陪伴与 AI 新奇体验敏感的年轻用户；对隐私敏感、不希望家用音频持续上云的亲子与独居场景用户；AI 玩具/桌搭品类厂商（作为可复用的 openvela 平台与参考产品）。
