## Official chain recovered from BK7258 documentation

```text
immutable BootROM BL1
        |
        +-- boot_flag -> primary_manifest -> primary_bl2
        |                    \-- fallback -> secondary_manifest -> secondary_bl2
        |
        +-- signed BL2 (MCUboot 1.9.0)
                    |
                    +-- signed primary_all (TFM-S + CPU0 app)
                    +-- signed secondary_all (TFM-S + CPU0 app)
```

`bk_security_boot.rst` states that BL1 is immutable BootROM code, verifies a
Manifest and BL2, and that BL2 verifies the later program(s). It also states
that BK7258 BL2 is open-source MCUboot 1.9.0. The partition guide defines
separate `primary_manifest`, `secondary_manifest`, `primary_bl2` and
`secondary_bl2` partitions. The documented minimum BL2 capacity is 128 KiB
logical (the BK 32+2 physical representation is larger).

The current project has a board-owned, recoverable BL1 proxy and one BL2
copy in the spare gap. Its successful hardware chain is useful development
evidence, but it is not yet the complete immutable-BL1 primary/secondary
layout described above.

## Source-level BK7236 reference and CP/AP consequence

The same checkout contains a buildable BK7236 TF-M/MCUboot reference. The
following files were read as source evidence, not copied into the BK7258
firmware:

| Source | What it establishes | Boundary |
|---|---|---|
| `components/tfm/tfm/bl1/bl1_1/main.c` | BL1_1 initializes the platform, copies BL1_2 into SRAM, hashes the complete fixed-size image, compares the stored root hash, and fails closed before jumping. | The stored hash is an OTP/TF-M contract; its BK7236 address and provisioning state are not BK7258 facts. |
| `components/tfm/tfm/bl1/bl1_2/main.c` | BL1_2 copies/decrypts a candidate, checks a decrypt marker, hashes the protected image data, checks a monotonic security counter, then tries image 0 and image 1 in order before handoff. | This is the TF-M encrypted BL2 image format, not the undocumented BK7258 BootROM Manifest ABI. |
| `components/tfm/tfm/bl1/bl1_2/lib/interface/image.h` | The reference image has a fixed header, protected version/counter fields, decrypt marker and payload; the protected region is what is hashed. | Do not use its field offsets or AES key source for BK7258 without hardware evidence. |
| `components/tfm/tfm/bl2/ext/mcuboot/bl2_main.c` | BL2 initializes flash/OTP, initializes the NV counter backend, calls `boot_go()`, and computes the final vector from the selected image/header. | BK7258 CP/AP needs a board-owned launch contract because the official reference launches one composite application image. |
| `components/tfm/tfm/platform/ext/target/beken/bk7236/partition/flash_layout.h` | MCUboot uses separate image IDs/areas for primary and secondary Manifest/BL2 and supports multiple later image areas. | The BK7236 offsets and generated partition header are not portable to BK7258. |

The pinned NuttX `boot_go()` implementation has an important multi-image
property: it validates each image ID independently, then `fill_rsp()` returns
the first enabled image's slot. It does not by itself guarantee that image 0
and image 1 came from the same A/B slot. Consequently the BK7258 board layer
must either (a) package CP+AP as one composite signed image, as the official
`primary_all` flow does, or (b) retain two MCUboot image IDs and enforce a
same-slot CP/AP pair before the final handoff. The current project chooses
(b) for the reversible CP/AP experiment; the board-owned same-slot pair gate
is now implemented and its cross-slot-only rejection is board-verified in
`2026-08-07-mcuboot-cp-ap-cross-slot-reject-board.md`.

## Manifest bytes generated by the official generic tool

Using a temporary EC-P256 key and a 16 KiB dummy image, the command used by
`bl1_sign.py`:

```text
secure_boot_tool -k key_desc.json -m primary_manifest.json -o <temporary-dir>
```

generated a deterministic 213-byte (`0xd5`) record. ECDSA `r||s` changes on
each signing, so the signature bytes are intentionally not compared. The
non-signature bytes are:

| Offset | Size | Meaning | Observed value/encoding |
|---:|---:|---|---|
| `0x00` | 4 | magic | `0xa1bc2fd8` little-endian |
| `0x04` | 4 | layout version | `0x00010001` |
| `0x08` | 4 | Manifest version | `mnft_ver` (the sample used `5`) |
| `0x0c` | 4 | total record length | `0xd5` |
| `0x10` | 4 | algorithm flags | `0x00030619` = EC256/SHA-256 |
| `0x14` | 4 | image count | `1` |
| `0x18` | 4 | image flags | `0` when unencrypted |
| `0x1c` | 4 | image version | `0` in the generic template |
| `0x20` | 4 | image static/XIP address | JSON `static_addr` |
| `0x24` | 4 | image load address | JSON `load_addr` |
| `0x28` | 4 | raw image length | exact source file length |
| `0x2c` | 4 | entry address | JSON `entry` |
| `0x30` | 32 | image digest | SHA-256 of the exact raw source bytes |
| `0x50` | 4 | reserved | zero when unencrypted |
| `0x54` | 65 | public key | SEC1 uncompressed `0x04 || X || Y` |
| `0x95` | 64 | Manifest signature | raw ECDSA P-256 `r || s` over bytes `0x00..0x94` |

The current `beken-candidate-v1` generator produces the same non-signature
field layout and adds `0xff` through the fixed 256-byte development record
window. Its verifier also checks that the unused BL2 copy-window tail is
erased. This is now a verified match to the generic Armino/IPSS tool shape,
not proof that the undocumented BK7258 BootROM consumes those bytes.

### Exact current-BL2 differential check

On 2026-08-08 the official tool and the repository generator were run with
the same temporary P-256 key, the current 10,708-byte `bl2.bin`, Manifest
version 5, XIP address `0x024d0000`, and load/entry address `0x28020000`.
Both outputs were exactly `0xd5` bytes.  A byte comparison proved:

```text
0x00..0x94  identical (header, descriptor, digest, and SEC1 public key)
0x95..0xd4  different (all 64 randomized ECDSA r||s bytes)
```

Therefore `beken-candidate-v1` is now a stable compatibility name for the
official release/v2.0.1 tool record, not merely a guessed field layout.  The
remaining uncertainty is exclusively the unprovisioned BK7258 BootROM's
acceptance/root-of-trust path, not the host record encoder.

When `is_enc=true`, the generic tool emits a different record (observed
length `0xf5`, algorithm flags `0x0003061d`, image flag `1`, and an AES key
blob at `0x50`). That encrypted path was not adopted or executed on the
board; OTP AES provisioning remains forbidden.

## Key hash and OTP relationship

`secure_boot_tool rotpk_hash` hashes the SEC1 public key (`0x04 || X || Y`)
with SHA-256. `gen_otp.py` places the BL1 hash at the documented
`0x4b100528..0x4b100548` range and reverses each 32-bit word for the BKFIL
configuration representation. The BK7258 TrustEngine documentation names
the corresponding OTP field `secure_boot_pk_hash` at offset `0x28` and LCS at
offset `0x68`.

The current board only has read-only OTP-shadow evidence: hash fields are
zero and LCS is `CM`. No key, lifecycle bit, secure-boot bit, AES key, or
lock bit was programmed.

## Signing and CRC order

The public BK7236/BK7258 security page gives a high-level order that is useful
for semantics, but the executable v3.1.1.9 packer source is the stronger
evidence for the artifact actually emitted by that SDK. Its `pack.py`,
`bl2_sign.py` and `partition.py` call chain is:

```text
logical verified code partitions -> merge primary_all
  -> MCUboot imgtool sign/pad primary_all
  -> AES encrypt (optional) -> add 32+2 Flash CRC
  -> physical tail/XIP-status placement
```

The current host reference now reproduces that order for the CP/AP logical
pair. It remains separate from the board-flashed path, which intentionally
uses a different, reversible board contract:

```text
logical CP/AP -> NuttX-pinned imgtool sign each image -> 32+2 CRC expand
-> paired slot placement -> board-owned MCUboot handoff
```

That path is hardware-tested as a CP/AP two-image MCUboot experiment, but it
must not be described as the official BK7258 `primary_all` packaging order.
The next implementation decision is whether to represent CP/AP as two
MCUboot images or as one merged `primary_all`-style image with a board-owned
CP/AP launch descriptor.

## Version and source boundary

The official generic tool reports MCUboot/imgtool `1.9.0`. The project keeps
the pinned NuttX MCUboot source and imgtool as the runtime/build authority;
the `bk_idk` tool is read-only reference material. The official v3.1.1.9
runtime SDK, NuttX, and `bk_idk` checkout are not modified or copied into the
firmware build by this investigation.

## Consequences

1. The candidate Manifest generator can remain a board-owned implementation,
   but its version must eventually be bound to the same release/security
   counter used by the signed BL2 image.
2. Full official-style reverse completion needs a secondary BL2 and a
   primary/secondary Manifest selection/fallback path; the current single
   BL2 development gap does not provide that behavior yet.
3. CP/AP adaptation is possible at the BL2 boundary, but TF-M/SPE, CPU0-only
   assumptions, AES, OTP and TrustEngine/FIA provisioning must not be copied
   from the BK7236 project as BK7258 facts.
