# BK7236 BootROM to BK7258 board BL1/MCUboot BL2 crosswalk

Date: 2026-08-08  
Input baseline: `2026-08-08-bk7236-bootrom-deep-reverse.md`  
Scope: architecture review only; no hardware or persistent-state operation

## Result

The current project is still on the intended BL1 -> MCUboot BL2 main line.
It already implements the reversible subset needed to exercise that chain,
but it is not yet a byte-for-byte BK7258 mask-ROM clone.  The newly recovered
BK7236 BootROM consumer validates the project's generic IPSS Manifest choice
and identifies three concrete semantic gaps: preferred-BL2 selection, the
OTP-backed Manifest-version floor, and the final hardware handoff ABI.

The official `release/v2.0.1` checkout also contains a BK7258-specific
`bk_security_boot.rst`.  It states the same two-stage architecture, describes
Primary/Secondary BL2 failover and identifies BL2 as MCUboot 1.9.0.  This is
stronger BK7258 architecture evidence than the BK7236 page, but the same tree
still leaves key integration as a `TODO`, disables Secure Boot in the board
configuration and contains no completed BK7258 BL1 source.  It therefore does
not contradict technical support's statement that the adaptation is missing.

## Official BK7258 wrapper evidence

The official `bk_idk` checkout contains a BK7258 wrapper that copies
`middleware/boards/bk7258/partitions/bl1_control.json` and invokes the same
security packaging tools.  The JSON exposes the expected control fields:

```text
magic = 0x4c725463 ("cTrL" in memory)
boot_flag
primary_manifest_addr
recovery_manifest_addr
pll_ena
security_boot_supported
security_boot_ena
security_boot_print_dis
jtag_dis
sw_fih_delay_ena
```

The official tree exposes two representations of the same three-page control
area.  The BK7258 documentation and `bl1_control.json` describe one 12 KiB
`bl1_control` role: vector page, boot-control page, then OTP-simulation page.
`partition.py` materializes only the first 4 KiB vector page, while concrete
BK7236 sample CSVs split the following page out as `boot_flag`.  This is an
SDK integration gap, not evidence for two different silicon ABIs.

The project staging profile follows the BK7258 documentation: one 12 KiB
partition. `make_bk7258_bl1_control.py` copies the BL2 vectors, emits the
recovered `0x28` record at offset `0x1000`, keeps secure boot/JTAG-disable
controls off, and leaves the OTP-simulation page erased.  The active legacy
layout still has no provider and therefore retains Primary -> Secondary
defaults.

However, that BK7258 file still has `Model ID = 7236` and
`security_boot_ena = 0`.  It is therefore useful as a scaffold and field-name
cross-reference, but not evidence that Beken completed or validated BK7258
Secure Boot.  This matches technical support's statement that BK7258 hardware
supports the function but the SDK adaptation is unfinished.

The BK7258 documentation adds the following intended semantics:

- eFuse bit 3 selects legacy-download versus Secure-Boot mode;
- immutable BL1 verifies Primary or Secondary BL2 according to `boot_flag`;
- when the preferred BL2 fails and the other passes, BL1 updates `boot_flag`;
- BL1 binds the Manifest public key to OTP, verifies the Manifest, hashes BL2
  and enforces the OTP image-version floor;
- BL2 is described as open-source MCUboot 1.9.0;
- the BL2 public-key/OTP integration section is explicitly still `TODO`.

The current project deliberately does not toggle eFuse bit 3 or persist an
official-format boot flag.  It can still implement read-only preference and
failover in a reversible development format.

Static reverse has now recovered the normal read-side encoding: BL1 reads the
first `0x28` bytes at raw Flash offset `0x1000`, requires magic `0x4c725463`,
uses preferred value `1` for Primary and `2` for Recovery, and obtains both
Manifest XIP addresses from the next two words.  The selected-image update in
the analyzed fallback path writes AON PMU register `0x4400000c` bit 0 and does
not program this Flash sector.  A separate calibration-source helper can
erase and rewrite the whole sector, but has no redundant or transactional
format.  Consequently there is no recovered power-loss-safe Flash protocol to
port, and the current BK7258 path intentionally remains read-only.

## Architecture decisions now justified by binary evidence

### Keep BL1 and BL2 as separate roles

BL1 authenticates and selects a small BL2.  BL2 is upstream MCUboot and owns
the CP/AP application pair.  Moving CP/AP policy back into BL1 would diverge
from the documented and reversed architecture.

### Keep the 128 KiB BL2 execution window

The BK7236 reference image happens to be about 72 KiB and is linked for SRAM;
that does not impose a 64 KiB BK7258 limit.  The board has already proven a
128 KiB copy/execution window.  Retaining that contract gives MCUboot room and
does not conflict with the recovered BL1 semantics because the descriptor
explicitly carries static, load, size and entry values.

### Keep the generic IPSS Manifest and remove no compatibility path yet

The consumer-side reverse confirms the same magic, field order, algorithm
selection, descriptor shape, ROTPK hashing and signature model produced by
`secure_boot_tool`.  The generic candidate is no longer an arbitrary format.
The older `BKBL1M2` parser remains a recoverable development fallback until a
separate migration removes it without stranding a board image.

### Keep the BK7258 CP/AP pair gate in BL2

BK7236 is single-core, so its BootROM cannot define BK7258 atomic CP/AP
selection.  Using MCUboot multi-image verification and then requiring equal
slot, version and security counter is a board extension, not a departure from
MCUboot.

## Next implementation slice

The next bounded code slice should not add another test framework.  It should:

1. represent the recovered `0x28`-byte BL1 boot_flag record in a small
   board-owned structure and parse it fail-closed;
2. allow a valid preferred-BL2 value to choose primary or secondary first,
   while retaining fallback to the other verified candidate;
3. keep the current primary-first behavior when the boot_flag record is erased
   or invalid, so development boards remain recoverable;
4. add a read-only Manifest-version-floor hook whose default remains zero;
5. never write OTP/eFuse or enable Secure Boot;
6. reuse the existing BL1 positive/negative build coverage and only add a
   focused host test if the new parser exposes a defect that cannot be checked
   by compilation.

The final handoff register ABI and physical BK7258 ROM alias remain reverse
engineering questions.  They should be addressed after this control-policy
slice, with a separately reviewed, finite read-only probe if static evidence
cannot close them.

The first such finite probe is complete and negative: official BK7258 headers
identify `0x44010008` as the boot-mode/Flash-select register, but both relevant
bits are already zero while the current image runs.  A watchdog plus core-reset
vector-catch attempt entered NMI at `0x020105a8` without changing secure VTOR
or exposing BootROM.  The board recovered through RTS reset and again reached
NuttShell.  This result rules out blindly copying the BK7236 reset tail; it
does not change the direct, vector-checked SRAM handoff used by the current
BK7258 BL1/BL2 chain.

## 2026-08-08 implementation checkpoint

The bounded policy and portable handoff slices above are now implemented:

- `boot_bl1_boot_flag_core.[ch]` decodes and validates the complete recovered
  `0x28`-byte boot_flag record, including both Manifest addresses and six
  boolean policy fields;
- absent, truncated, oversized, erased, bad-magic, bad-address and
  unknown-flag inputs all preserve Primary -> Secondary recovery order;
- only a complete valid record with flag `2` selects Secondary -> Primary;
- `boot_main.c` consumes the returned order but deliberately passes an absent
  provider, so the current runtime order remains Primary -> Secondary;
- both the legacy development Manifest and the IPSS candidate use the same
  version-floor helper;
- the board override reads the v3.1.1.9 BK7258 BL1 counter shadow at
  `0x4b111088` and decodes its consecutive LSB-one unary format; the weak
  zero-floor hook remains only for host builds;
- `boot_bl1_handoff_core.[ch]` checks that the XIP and SRAM MSP/Reset words
  match exactly and fall inside the proven 128 KiB BL2 window;
- no boot-flag, Flash, OTP or eFuse writer was added.

Host coverage exercises the input/status matrix, vector boundaries, malformed
unary counter values and version floors `0`, `5` and `UINT32_MAX`.  The Arm freestanding objects
compile with `-Werror`; the full BL1 build and partition check pass.  A
matching sparse board deployment subsequently reached BL2, the paired
MCUboot handoff and NuttShell; see the deep-reverse record for the capture.

The following BL2 read-only slice is now compiled, re-signed and deployed:
v3.1.1.9's generated BK7258 OTP map assigns a 64-byte BL2
counter to physical OTP `0x200`, corresponding to verified Dubhe shadow
`0x4b111100..0x4b11113f`.  The backend counts all programmed bits, matching
Beken's TF-M NV-counter decoder, and takes the maximum of that count and the
existing compile-time development floor.  Its disassembly contains exactly
16 volatile loads across that window and no MMIO store.  The MCUboot update
hook remains read-only and cannot advance the floor.

The BL1 packaging boundary now accepts an external P-256 private-key path,
derives a public-only C source in the private build directory, links that
source as the BL1 development root, and emits matching primary/secondary
Manifest records.  A random key without that explicit generated-root path is
still rejected by the legacy fixed-root gate.  The private key was deleted
after packaging; the public C source, Manifest records and validated binaries
were retained with capture `logs/bk7258-auto-debug/20260808-101553`.

The matching sparse deployment wrote the 68 KiB boot envelope and both 16 KiB
BL2 CRC streams without touching LittleFS or OTP/eFuse.  It reached
`B1PRIMARY`, `B2INIT`, `B2GOOK`, `B2SELA`, `B2APOK`, `B2HANDOFF` and NuttShell.
This closes the earlier deployment deferral and proves that the external-root
build path and the read-only BL2 counter backend coexist on the board.
