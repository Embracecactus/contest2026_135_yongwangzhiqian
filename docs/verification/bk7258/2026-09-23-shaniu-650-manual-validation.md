以上是代理指标，未包含用户停说到录音线程结束的 VAD 尾延迟，不是声学出声时间。本轮没有证明首句已提速；真正的已确认有效正文增量流水线仍未实现。不得通过朗读工具决策中间文字、关闭工具或额外无工具请求伪装提速。

### 2. TTS 连续性、语速及唤醒应答

三次成功输出均记录 `rebuffer=0`。无工具回合 PCM 2324480 字节，16kHz/单声道/16bit 对应约 72.64 秒音频，队列峰值 65536 字节、最大接收间隔 349ms、完成返回 0。这证明该样本连续输出，不能扩大为全部网络条件稳定。

主要等待发生在首段播放之前；不得把总合成耗时误当成首句等待，也不得通过加快语速解决等待。保留已有有界队列和 Media 单一所有权。官方 Media EOF 重复报错仍未解决，替代 adapter 主机检查不能代替实际 Media 验收。

### 4. K2 关机后再次重启：本轮仍失败

两次实际日志都显示：接受 K2 请求 → 重启进入 soft-off → `entering super-deep; wake gpio=12` → HardFault → 再次正常启动。

故障寄存器重复为 `H=40000000 C=00020000`。按锁定 NuttX 定义分别为 HFSR FORCED 与 CFSR INVSTATE。这不是已证明的正常睡眠被按键唤醒；精确故障 PC/调用点尚未得到，不能只凭寄存器就宣布某个 SDK 函数是根因。

650 的 SRAM 最小边界调整和 WFI 包装没有解决该实板问题。下一轮必须追到睡眠入口、调用/返回状态及必要 RAM 闭包，不能恢复会导致 649 OOM 的整对象搬移，也不能以黑屏、关机图标或自动重启冒充关机成功。无需用户继续重复按键来证明同一个已复现故障。
