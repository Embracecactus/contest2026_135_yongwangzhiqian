# 01｜BK7258 T5-AI 小白学习路线

这条路线的目标不是让你尽快复制一条命令，而是让你逐步具备三种能力：

1. **定位**：知道一个问题属于工作区、构建、启动、内核还是外设子系统；
2. **追踪**：能从配置入口走到源码、链接产物和运行证据；
3. **表达**：能把已证实事实、教学简化和待确认假设分开写清楚。

## 4. L1：读懂嵌入式源码所需的最小基础

### 学什么

按未来 `10-foundations/` 的顺序学习：

1. 二进制、十六进制、位掩码、移位；
2. C 指针、数组、函数指针、结构体、`const` 与 `volatile`；
3. 内存映射 I/O：地址、寄存器、字段和读改写；
4. Cortex-M 异常、NVIC、向量表、栈和临界区的基本概念；
5. 段、符号、链接地址、加载地址、ELF 与固件镜像的关系。

### 练习方式

只做纸面或只读练习，例如：

- 把一个十六进制值展开成位；
- 在头文件中找一个结构体声明和其使用者；
- 解释为什么普通内存变量和硬件寄存器不能总用同一种访问假设；
- 在链接脚本中认出 `text`、`data`、`bss` 等概念，不修改脚本。

### 退出条件

你可以读懂常见寄存器表达式、函数指针声明和链接脚本的基本段落；遇到不懂的 ARM 术语时，知道应找架构文档而不是从文件名猜答案。

## 5. L2：仓库、配置和构建图

### 学什么

未来 `20-boot-and-build/` 前两篇覆盖：

- `repo` manifest 与 `<linkfile>` 的所有权关系；
- Kconfig 定义、defconfig 默认值、生成 `.config` 的区别；
- classic Make 与 CMake 是两条构建后端，不能看到一个文件就假定它是当前生效入口；
- 源文件如何被条件加入目标；
- 链接脚本、post-build、打包脚本分别改变什么。

### 推荐追踪顺序

```text
manifest 所有权
  → Kconfig 符号定义
  → defconfig 请求值
  → 生成 .config 有效值
  → Make/CMake 源文件选择
  → 编译对象
  → ELF/map
  → post-build / 最终镜像
```

### 退出条件

给你一个 `.c` 文件，你能列出证明“它进入最终镜像”所需的证据，而不是只回答“目录里有这个文件”。

## 6. L3：启动链

### 学什么

未来启动章节从抽象到具体解释：

1. 复位后谁最先拥有控制权；
2. bootloader、应用镜像和 NuttX 启动入口各自的职责；
3. 向量表、初始栈、复位入口、C 运行时初始化；
4. 链接布局与打包布局为什么必须同时正确；
5. 第一条可观察 UART 输出能证明什么、又不能证明什么。

### 退出条件

你能画出一张不超过十个节点的启动主链，并在每个节点旁写出“来源在哪里”。如果某一步只是推测，应明确标为待确认。

## 7. L4：NuttX 核心分层

### 学什么

未来 `30-nuttx-core/` 按以下顺序展开：

- `arch`、`chip`、`board` 和通用内核代码如何分工；
- 启动、调度器、idle 线程和 board bring-up 的概念关系；
- IRQ attach/enable/dispatch 与临界区；
- system tick、时间换算与调度时间基准；
- NSH、procfs 等用户可观察入口如何连接到底层能力。

### 退出条件

面对一个运行时行为，你能先判断它更可能属于架构层、芯片层、板层、内核层还是应用层，并说明判断依据。

## 8. L5：按固定模板学习每个 subsystem

建议顺序：

1. UART / console：最直观的观察通道；
2. clocks / reset / DVFS：理解“代码速度”和外设时基从哪里来；
3. interrupt / vector：理解异步事件怎样进入内核；
4. timer / tick：连接硬件计时、IRQ 与调度时间；
5. watchdog：理解健康监控、复位与调试干扰；
6. GPIO：理解 NuttX upper/lower half 驱动模型、`/dev/gpioN` 用户态接口与中断路由；
7. flash / MTD / filesystem：理解从硬件存储到文件接口的分层；
8. SDK boundary：理解外部库、适配层和所有权；
9. multicore basics：最后再引入核间边界，避免过早扩大问题空间。

每个子系统固定使用五篇模板：

| 顺序 | 文件 | 必须回答的问题 |
|---|---|---|
| 1 | `01-mental-model.md` | 它解决什么问题？输入、输出、状态、失败方式是什么？ |
| 2 | `02-source-and-config-map.md` | Kconfig、构建入口、头文件、实现和所有者仓库在哪里？ |
| 3 | `03-runtime-call-flow.md` | 从入口到硬件/内核服务经过哪些层和上下文？ |
| 4 | `04-safe-observation-lab.md` | 如何先用只读或最小扰动方法观察？停止和恢复条件是什么？ |
| 5 | `05-evidence-and-review.md` | 哪些结论是静态、构建、产物或板端证据？常见误判是什么？ |

### 退出条件

你能选择一个子系统，按同一模板独立写出来源地图和主调用路径，并指出至少一个教学简化点。

## 9. L6：只读追踪与可重复观察

### 学什么

未来 `50-guided-labs/` 先练五件事：

- 从 Kconfig 符号追到有效配置；
- 从一个符号追到对象和 ELF；
- 从 map 文件判断符号归属；
- 设计不改变系统状态的观察；
- 写一条别人能复查的证据记录。

### 证据阶梯

```text
源码可见
  ≠ 配置生效
  ≠ 编译成功
  ≠ 符号进入最终产物
  ≠ 硬件执行到该路径
  ≠ 行为在重复实验中稳定
```

每向右移动一步，都需要新增证据，不能用前一步代替。

### 退出条件

你的记录至少包含：问题、基线 commit、相关路径、命令或观察方法、实际输出摘要、结论边界、未确认项和下一最小步骤。

## 10. L7：小改动与独立验证

只有在前六级完成、实施任务明确授权后，才进入写操作：

1. 先记录工作树状态和基线 commit；
2. 明确只修改哪个拥有者仓库；
3. 先写预期和失败判据；
4. 做一个最小改动；
5. 分别验证配置、构建、产物和运行；
6. 更新实施证据；
7. 最后更新教学解释。

教程本身不会把“可以理解的实验”自动变成“已授权的构建、烧录或板测”。实施动作始终遵守单独的授权门禁。

## 11. 每次学习都用同一个六步循环

```text
提问 → 定位所有者 → 固定版本 → 只读追踪 → 收集证据 → 写出边界
```

建议笔记模板：

```markdown
### 问题

### 所有者与路径

### source ref / commit

### 我看到的证据

### 我能下的结论

### 教学简化或类比

### 仍待确认

### 下一最小只读步骤
```

如果无法填写 `source ref / commit`，说明这次学习还没有建立可复查基线，应先回到[权威来源地图](03-authoritative-source-map.md)。
